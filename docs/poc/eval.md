# 根拠文の評価表（Phase 1）

評価軸（5段階）：① 数値の正確性 ② 論理の順序（事実→基準→算定→結論） ③ コンプライアンス ④ 営業が話せるか

## 実行条件

- 実行：`pnpm poc all`（出力：`docs/poc/runs/<case>/result.md`）
- 本評価は **定型文モード**（APIキー未設定のため）の出力に対するもの。LLM モードの評価は下記「LLM モードでの評価手順」で実施する
- 自動チェック結果：3ケースとも **数値グラウンディング違反 0／マスキング違反 0／禁止表現 0／必須注記の欠落 0**（`packages/llm/test/narrative.test.ts`・`pnpm poc`）

### 定型文モードの弱点（LLM モードで改善を狙う点）

1. 3案とも根拠1〜3文目（事実・基準・算定）が同じ文面になり、案ごとの差は4文目だけ
2. 商談ログの発言（「息子に継がせたい」「元本割れは不安」など）を根拠文に織り込めない（トークスクリプトの課題提起でのみ引用）
3. 予算の目安が小さい会社（ケースC）では「調整した」旨の注記が多くなり読みにくい

## プロンプト改善の記録

APIキーがない環境で開発したため、下記は実出力の比較ではなく、設計レビューと偽クライアントによる検証（`narrative.test.ts`）に基づく改訂です。

| 版 | 変更 | 狙い・根拠 |
|---|---|---|
| v1 | 仕様 §9 の system プロンプト＋CALC_RESULT（calcId, value, formula）＋PLANS を渡して一から作文 | 基本形 |
| v2 | 定型文の下書き（DRAFT）を渡し「数値と論理はそのまま、会社の状況に合わせて書き直す」方式に変更。金額表記（「6億7,751万円」、概数には「約」）を system に明記 | 数値捏造・計算のリスクを下げる。グラウンディング検証で「約」表記を許容範囲で扱えるようにした |
| v3 | 顧客発言の引用は数値を含まないものに限定。FEEDBACK ブロック（前回の違反内容と言い換え方針）を再生成時に付与。cautions は DRAFT の必須注記を残す指示を追加 | 再生成で同じ違反を繰り返さないようにする。必須注記はコード側でも強制追加 |

現在の版：`p3-prompts-2026.09.3`（`packages/llm/src/prompts.ts`、本文は `packages/llm/prompts/index.ts`）

## LLM モードでの評価手順

```bash
export ANTHROPIC_API_KEY=...        # 3ケースで Step2＋Step5 を実行（有料）
pnpm poc all                         # docs/poc/runs/*/result.md に出力。source が llm / mixed / template のいずれかを表示
pnpm bench 3                         # レイテンシ・トークン・再生成率・ブロック率
```

各 `result.md` を上表の軸で採点し、この表に「LLM v3」列を追加してください。再生成率が高い違反の種類（`compliance.issues` の type）はプロンプトの FEEDBACK と system の禁止事項に反映します。
