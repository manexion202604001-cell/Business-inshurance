## 計算（engine）

| # | 仮定・判断 | 理由 | 変更容易性 |
|---|---|---|---|
| E01 | 金額はすべて万円・整数、四捨五入（0.5 は切り上げ）。途中計算は丸めずに最後に丸める（方式Aの納税準備資金は丸めた①②から計算） | §13 の期待値（22,751 など）と一致させるため | ○ |
| E02 | 既定の採用方式は運転資金方式（B）。設定 `adoptedMethod` で切替 | §7.3 の初期値 | ◎ |
| E03 | 経営立て直し資金は「月間人件費×6か月」（方式A-B）を採用。3年間の損失試算（A-A）は未実装 | 業種別データ・売上予測の入力がないため | △ |
| E04 | 任意項目が未入力のときの仮置き：月間人件費＝年商×20%÷12、その他固定費＝年商×5%÷12、月返済＝借入金÷(10年×12)、一括返済＝0、法定相続人＝2人、勇退年齢＝70歳（現年齢以上）。すべて「仮置き」バッジを付けて表示し、タップで修正→Step3以降を再実行 | 生成を止めない（§8.1）。比率は一般的な中小企業の目安として置いた仮の値 | ◎ 設定値 |
| E05 | 商談ログに数値があり、フォームが空欄の任意項目はログの値で補完し「商談ログから補完（要確認）」として仮置き扱い。フォームとログが10%以上ずれた項目は conflicts として表示し、計算はフォームの値を優先 | 入力値を正とする（誤抽出で計算が変わらないように） | ○ |
| E06 | 保険料予算の目安：経常利益が未入力または0以下のときは「最小＝年商×0.5%、バランス＝×1.0%、最大＝×2.0%」（経常利益比率 5:10:20 と同じ比で拡張） | §7.4「年商×0.5%を仮置き」をどの段階に当てるか明記がないため、最小に当てて比率を保った | ◎ |
| E07 | 退職所得控除の勤続年数は「役員在任年数＋勇退までの年数」を1年未満切り上げ。特定役員退職手当等（勤続5年以下）は1/2課税なし。短期退職手当等（300万円超部分）は未対応 | §7.3 の算式と §13 の期待値 | ○ |
| E08 | 「役員報酬に上乗せした場合」の税額は、給与所得控除が上限（195万円）に達している前提で、基礎控除48万円のみ考慮した増加額（所得税×1.021＋住民税10%）の概算。社会保険料は考慮外 | 比較の目的は退職所得の仕組み（控除・1/2課税）の説明であり、厳密な手取り計算ではないため | ○ |
| E09 | 税務区分は全期払を前提。**短期払（払込期間＜保険期間）は Phase 2 でも未対応**とし、資料に「区分により取扱いが異なります」と注記 | 年換算保険料相当額の計算が契約ごとに異なり、概算の域を超えるため。設計書で確認する運用 | △ |
| E10 | 区分2・3の資産計上期間（保険期間の40%）や取崩開始（75%）が端数年になる場合は年単位で按分 | 通達は月単位のため、年払の概算として按分が最も近い | ○ |
| E11 | 区分4は「最高解約返戻率となる年」を資産計上期間の終わりとし、年度末解約返戻金の配列があれば延長規定（増加額÷年換算保険料＞7/10）と「返戻金額が最大の年」以降の取崩しを計算。最低5年（保険期間10年未満は50%）を適用 | 通達9-3-5の2 | ○ |
| E12 | 30万円基準は `annualizedPremiumPerInsured`（他社合算）で判定。プラン内の概算では当該構成の保険料のみで判定 | 他社契約の保険料が入力されない場合がある | ○ |

## プラン構成（ロジック辞書・参考料率）

| # | 仮定・判断 | 理由 | 変更容易性 |
|---|---|---|---|
| P01 | **参考料率は開発用サンプル**（簡易ゴンペルツ死亡率＋平準保険料で生成、`packages/knowledge/scripts/generate-sample-rates.ts`）。実在の商品の料率ではない旨を資料の必須注記に自動追加。管理画面の CSV インポートで実料率に置換できる | 料率がないと予算内での保障額調整・税務区分・返戻率ピークの説明ができず、テスト利用が成立しないため | ◎ CSV 取込（「サンプル料率を置き換えて追加」） |
| P02 | 保険料の目安は参考料率×保障額の±15%の幅で表示 | 参考値であることを明示するため | ◎ |
| P03 | 3案の割付：最小＝不足額のうち借入金（借入0なら運転資金＋一括返済分）を最安のカテゴリで。バランス＝不足額全額＋勇退退職金（物価考慮後）の50%を返戻率ピークで準備。最大＝不足額全額＋勇退退職金100%＋R04/R05/R06の追加。予算超過時は「追加の備え→退職金準備→保障額」の順に縮小（退職金準備は予算の50%まで優先確保）し、調整前の参考保険料を注記 | §8.2 の方針を、各案の性格が崩れないように具体化 | ○ |
| P04 | 退職金準備の保障額は「保険料×ピーク年数×ピーク返戻率＝目標額」から逆算。ピーク年齢が勇退年齢に最も近い保険期間の料率を選択 | 返戻率ピークを勇退時期に合わせる（R03） | ○ |
| P05 | 第三分野の保障額＝役員報酬月額×36か月、福利厚生プラン＝従業員数×300万円（保険料は設計書にて）、終身保険＝死亡退職金の非課税枠相当 | 目安がないため設定値として置いた | ◎ |
| P06 | ケースCの期待ルールに R05 が含まれないため、商談ログの「従業員の退職金は中退共に入ってる」を従業員退職金準備済みと判定するルールにした | §13 の期待ルールとの整合 | ○ |
| P07 | JSON Logic は必要な演算子（var, 比較, and/or/!, in, 四則, min/max, if）のみ自前実装。null との比較は常に false | 依存を減らし、欠損データでルールが誤発火しないようにするため | ○ |

## LLM・コンプライアンス

| # | 仮定・判断 | 理由 | 変更容易性 |
|---|---|---|---|
| L01 | 構造化出力は tool use ではなく **Structured Outputs（`messages.parse` + zod）** を使用 | JSON Schema 準拠が保証され、現行 SDK の推奨方式。仕様の意図（スキーマで縛る）は同じ | ○ |
| L02 | モデルは仕様どおり MAIN=`claude-sonnet-5`、FAST=`claude-haiku-4-5-20251001`（環境変数で変更可）。Sonnet 5 は temperature を受け付けないため、温度指定（Step2=0／Step5=0.4）は Haiku 系のみに適用し、Sonnet 5 は `effort: low` で呼ぶ | 新しいモデルではサンプリングパラメータが廃止されているため | ◎ |
| L03 | **APIキーがない場合は「定型文モード」**で動作（Step2＝ルール抽出、Step5＝定型文テンプレート）。キーがあれば自動で LLM を使う（`P3_LLM_MODE=auto/on/off`） | §14 のフォールバック要件を満たし、APIキーなしでもテスト利用できるようにするため | ◎ |
| L04 | LLM には定型文の下書き（DRAFT）と計算結果（calcId付き）を渡し、「数値と論理はそのまま、会社の状況に合わせて書き直す」よう指示 | 数値捏造の余地を最小にしつつ、個社に合わせた言語化をさせるため | ○ |
| L05 | 数値グラウンディング：文中の数値（億/万/千/漢数字/カンマ/%/年/歳/か月/倍/名）を抽出し、計算結果・入力値・統計値・設定値・税務定数の集合と照合。整数表記は完全一致、「約」や小数表記（4.9億円 等）は表示精度の半分まで許容。12以下の単位なし整数（「3つの案」など）と日付（2026年、令和7年）は対象外 | 丸め表示を許しつつ、計算していない数値を検出するため | ○ |
| L06 | 違反時は最大2回まで違反内容をフィードバックして再生成し、それでも残る違反は**該当フィールドだけ**定型文に差し替え（`source=mixed`）。必須注記（カテゴリの mandatoryDisclaimers）はコード側で必ず追加 | §3 原則2 | ○ |
| L07 | FAST モデルによるダブルチェック（固有名詞・実質的な節税訴求）は **warning 扱い**（ブロックしない）。辞書・正規表現の検出は error（ブロック） | LLM 判定は誤検知があるため、人手確認に回す | ◎ |
| L08 | 「節税」は禁止表現だが、必須注記「通期での節税効果はありません」など否定の文脈は許可リスト（allowContext）で除外 | 注記自体がブロックされるのを防ぐため | ◎ |
| L09 | 顧客の発言引用（evidenceQuote）はログに実在する部分文字列のみ採用。トークスクリプトには数値を含まない引用だけを使う | 捏造引用とグラウンディング違反を防ぐため | ○ |
| L10 | 話者ラベルは除去せず「名前：」形式に統一（VTT/SRT のタイムスタンプ・キュー番号は除去） | 顧客発言と営業発言を区別して抽出するため | ○ |
| L11 | マスキングは入力時（Step1）・LLM出力後（Step5/6）・レンダリング直後（Step7）・表示／PDF化直前（API）の4か所。ナレッジ投入時のマスキングは管理画面の保存時ではなく生成時の走査で担保 | 仕様 §7.6 の4か所に相当。ナレッジには資料名以外の社名を持たせない運用 | ○ |
| L12 | 営業メモの「内部参照」（実商品との対応表）は manager 以上がチェックした場合のみ表示。レンダリング後の走査からは除外するが、顧客向け資料には構造上含まれない | §7.6 | ○ |
| L13 | 個人名のマスキングは未対応（メール・電話番号のみ、`P3_MASK_PII=1`） | 日本語の人名検出は誤検知が多い | △ |

## 運用

| # | 仮定・判断 | 理由 | 変更容易性 |
|---|---|---|---|
| O01 | ナレッジは「編集中の下書き（テーブル）」→「版の公開（スナップショットJSON）」の二段構え。生成は最新の公開版を使い、案件には版IDを記録。旧案件の表示・PDFは作成時の版で再レンダリング | §7「生成時の版を Case.knowledgeVersion に記録」 | ○ |
| O02 | 承認フローは設定（requireApproval）で ON/OFF。ON のとき顧客向け資料（サマリー・設計書・スライド・共有）は承認までロック、営業メモは対象外 | 組織の募集文書管理ルールに合わせるため | ◎ |
| O03 | 共有リンクは有効期限付き（既定7日、最大30日）で、閲覧には社内ログインが必要 | 「社内のみ」の要件 | ◎ |
| O04 | データ保持は `retentionDays`（既定365日）を超えた案件を `pnpm retention` で削除（cron 等で定期実行する想定） | バッチ実行の仕組みを持たないため | ○ |
| O05 | 本番DBの保存時暗号化は PostgreSQL／ストレージ側の機能（TDE・ディスク暗号化）で担保する前提。アプリ側の項目暗号化は未実装 | インフラ構成に依存するため | △ |
